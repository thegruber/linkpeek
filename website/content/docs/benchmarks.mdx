I measured linkpeek and five other link preview packages on <BenchmarkDate />, with the same pages, the same local server and the same correctness check. The harness is open, so you can run it yourself. The pages are served locally, which means the numbers show library time without network latency ([why a live preview takes longer](#live)). Where another package is the better fit, the [library comparison](/guides/link-preview-library-comparison/) says so.

<BenchmarkHighlights />

## Large pages [#large-page]

Each package previews the same 500 kB page whose metadata sits in the `<head>`. linkpeek stops reading after the head and cancels the response stream, so most of the body is never read or parsed.

<BenchmarkChart kind="large" />

## Small pages [#small-pages]

On small pages the packages are within about two milliseconds of each other, and real network latency dominates. `unfurl.js` was faster than linkpeek on every small fixture in this run: it requests pages with `node-fetch` over Node's `http` module, while linkpeek uses the platform `fetch` so the same code runs on Bun, Deno and Workers. Among the packages measured on `fetch`, linkpeek was fastest on every page.

<BenchmarkChart kind="small" />

## Install footprint [#size]

linkpeek has one runtime dependency, `htmlparser2`. A small install matters most for serverless cold starts, container images and edge bundles.

<BenchmarkChart kind="install" />

## Bytes read from a 500 kB page [#stream]

The local stream probe serves a controlled 500 kB response in 1 kB chunks and records how much the parser requested.

| Mode | Source bytes requested | Configured ceiling | 500 kB page |
| --- | --- | --- | --- |
| **Fast** (default) | **2 kB** | 30 kB | Stops after `</head>` |
| Quality | ~202 kB | 200 kB | Continues for body fallbacks |

“Source bytes” includes one 1 kB chunk that was already queued in the stream; the retained-byte ceiling itself is exact. The figures count requested chunks, not bytes on the wire.

## Benchmarks and a live preview [#live]

These runs use a local server, so they measure the library, not the internet. A live preview also waits for the target site: DNS, the connection, TLS and the server's own response time. That wait is usually far longer than the library's work, and no parser can shorten it.

The homepage demo shows the two apart. "Site" is the time until the target's response headers arrive, summed over redirects. "Reading head" is linkpeek streaming the rest of the `<head>` and parsing it. On a real network, reading only the head still saves time on large pages, because linkpeek stops downloading after `</head>` instead of transferring the whole document.

## Method [#method]

<BenchmarkMethod />

Timings depend on hardware: an earlier run on Apple silicon measured lower absolute numbers with the same ordering on the large page. The [comparison notes](https://github.com/thegruber/linkpeek/blob/main/docs/comparison.md) keep every dated result, and the [raw JSON runs](https://github.com/thegruber/linkpeek/tree/main/benchmarks/competitive/results) include commit and environment details.

## Run the benchmarks [#reproduce]

```bash
npm ci
npm run benchmark

npm run build
cd benchmarks/competitive
npm ci
npm run bench -- --json
```

The competitive lockfile pins every compared version, and every timed preview must extract the expected title. The live benchmarks are network smoke tests, and I don't use them to compare packages.
