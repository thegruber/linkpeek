## Recommendation

Keep the small SAX-parser/native-fetch architecture and fast default. There are important security-maintenance, compatibility, and correctness fixes to make before the next release. A framework rewrite, new runtime dependency, or blanket upgrade to every latest major is not justified by this audit.

The existing tests and package checks pass, but **the full quality gate fails on dependency advisories**. Separately, targeted probes reproduce defects that the current suite does not cover. The most useful performance fix is eliminating avoidable response-body waits, rather than optimizing already-small parser timings.

Priority meanings: **P1** = address before the next release or production maintenance cycle; **P2** = concrete next correctness/assurance work; **P3** = lower-impact maintenance or evidence improvement. These are work priorities, not CVSS scores.

### A2. Keep origin isolation across meta-refresh — P1

**Owner:** [src/index.ts:64–69](../src/index.ts), [src/fetch.ts:239–247](../src/fetch.ts). The documented custom-header isolation is in [README.md:276](../README.md).

`preview()` passes the original options to a new `fetchUrl(refreshUrl, options)`. That new invocation treats the refresh destination as its starting origin and sends the original custom headers. The HTTP redirect path correctly strips them, so an HTTP A → B followed by B → B meta-refresh can also reintroduce A's headers.

A public API probe with `X-Preview-Context: audit-marker` and a refresh from `https://first.example` to `https://second.example` observes the marker on **both** requests. No actual secrets or external requests are used in this probe. Common Authorization/Cookie names remain blocked; this finding concerns otherwise permitted origin-specific headers.

Preserve the original trust boundary through both redirect mechanisms. Test direct cross-origin refresh and the HTTP-then-refresh chain at `preview()`, retaining same-origin behavior. Do not implement the fix by comparing only the refresh to the last HTTP destination.

### A3. Patch actual Node installations — P1 maintenance

The workspace has **Node 24.18.0**, including embedded Undici **7.28.0**. The current security patches are **22.23.4, 24.22.1, and 26.12.1**. Node's October 21 release addresses DNS, TLS/IP validation, Brotli, and dependency security issues. Update development/release hosts and deployed consumers; changing package-lock.json does not patch built-in fetch. This audit did not demonstrate exploitation of the old runtime. [Official Node security bulletin](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases).

Keep the Node 22/24/26 matrix. Node 20 is EOL; the current official schedule does not justify adding a stable Node 27 lane yet. Check future support against the [live Node release schedule](https://github.com/nodejs/Release/blob/main/schedule.json), rather than assuming the historical odd/even cadence.

### A4. Correct the CommonJS support floor — P2

Keep `dist/index.js`, `.cjs`, `.d.ts`, and `.d.cts` contracts intact.

An initial 300 ms trial was too sensitive to host load and failed its positive control; it was discarded. The recorded 2,000 ms trial uses an 8,000 ms delayed body and passes the charset-positive control on both tested Node patches.

The [HTML parsing standard](https://html.spec.whatwg.org/multipage/parsing.html#determining-the-character-encoding) gives BOM detection precedence, skips comments during encoding prescan, and uses separate template parsing context. [JSON-LD graph-object syntax](https://www.w3.org/TR/json-ld11/#graph-objects) supports the B6 input form.

Other API behavior to clarify during follow-up: meta-refresh currently receives a fresh timeout and HTTP-redirect budget, and failure returns the first page's metadata. Thus timeout is not necessarily a total preview deadline. This is visible in `src/index.ts:64–79`; it is a contract-design question, not counted as another confirmed defect here.

Results are local measurements, not production latency or competitive claims. This is a shared two-vCPU VM with other audit/cache activity, not an isolated benchmark host; sample variation is material. There is no same-hardware older-version baseline, so these results do not establish a regression.

The 500,911-byte **quality parser benchmark parses the entire supplied string**. It is not the same workload as `preview(..., presets.quality)`, which retains at most 200,000 decoded response bytes. `parseHTML()` accepts an already available string and does not apply fetch byte limits.

The controlled 1,024-byte-chunk stream probe requested **2,048 source bytes in fast mode** and **201,728 in quality mode**, canceling both streams. These include stream read-ahead and are not exact retained or wire-byte counts. Existing tests separately enforce exact retained-byte limits. The benchmark always supplies an HTTP charset, so it misses B1's stall condition.

Measured package footprint: **30,813 bytes packed**, **105,303 unpacked**, **8 files**; ESM entry **30,171 raw / 8,164 gzip bytes**. The entry measurement excludes htmlparser2 and its transitive dependencies. There is one direct runtime dependency and six dependency packages in the complete locked production tree; “one dependency” should be qualified as direct.

Recommended performance work, in order:
1. Fix B1's avoidable prescan wait and B8's zero-budget body read. Measure these as lifecycle behavior with deterministic fixtures, not flaky absolute timing thresholds.
2. Add delayed-body/no-charset, split-encoding, long-head, late JSON-LD, and compressed-response cases to the performance evidence where they cover distinct behavior. Preserve the fast/quality distinction; do not globally raise the default cap to recover every late metadata field.
3. Add **extraction correctness checks before accepting competitive timing rows**. `benchmarks/competitive/bench.mjs:143–162` prints only the last warmup title and discards timed return values: a fast incorrect result can currently be ranked as a success. Record versions, commit, options, and environment with machine-readable results. Retain explicit unsupported-adapter outcomes.
4. Before optimizing copies or combining parsers, profile on representative workloads. `fetch.ts` currently buffers/copies and decodes again for final extraction; quality plus meta-refresh can parse the head again. These are optimization candidates, not measured bottlenecks. The retained-data budget is not a bound on total RSS, decompressor allocations, or caller concurrency.
5. For deployment capacity decisions, measure concurrent previews, p95/p99 latency, memory/GC, cold imports, and cancellation under the actual runtime/network policy. This audit did not execute a sustained load test or CPU/heap profile. Existing microbenchmarks cannot answer those capacity questions.

The dated August competitor measurements in [docs/comparison.md](comparison.md) are historical, explicitly caveated evidence. No fresh competitor speed comparison was run, and no old numbers were relabeled. Updating the benchmark dependencies will require rerunning before making new comparison claims. The playground's `~7 KB gzipped` footer (`examples/playground/index.ts:109`) is already inconsistent with the dated entry measurement and this run; replace it with a scoped, dated link rather than another unqualified hardcoded number.

## Tests, examples, documentation, and accessibility

### C1. Repair the timeout assertion — P2

In [test/fetch.test.ts:308–330](../test/fetch.test.ts), “throws a typed TIMEOUT error after the configured timeout” puts its error assertions inside `.catch()`. If the promise unexpectedly fulfills, the awaited catch-chain fulfills too, skipping those assertions. Register an awaited rejection assertion before advancing fake timers, or explicitly fail fulfillment. Preserve the error type/code checks. A stalled-body timeout test is independently useful because a timeout mistakenly cleared at response headers would still pass the current header-wait test.

Coverage is high in aggregate but does not prove these contracts. `src/index.ts` branch coverage is **69.56%** despite overall **89.71%**. Add tests for observed behavior gaps, not merely to raise a number. The new cross-origin meta-refresh regression belongs at `preview()`; do not duplicate every redirect test across layers.

### C2. Fix the React example's full request journey — P2

[examples/react-preview-card/LinkPreview.tsx:16–25](../examples/react-preview-card/LinkPreview.tsx) has no effect cleanup: a slow request for URL A can overwrite a later successful URL B, including its link destination; an obsolete rejection can overwrite current success. Add cancellation plus a stale-result guard for both success and error. [React's official effect guidance](https://react.dev/reference/react/useEffect#fetching-data-with-effects).

The same component checks only the API response's `res.ok` and omits target `statusCode`. Recommended API routes return HTTP 200 for a resolved preview whose target was 404/500. Include `statusCode` and render the intended broken-link state for target errors, matching the README's existing contract. Verify out-of-order requests, old rejection, API failure, upstream 404, success, loading, keyboard activation, and accessible status announcements. These are source-confirmed control-flow issues; a React/browser harness was not executed.

### C3. Repair example accessibility and verify scroll regions — P2

- [examples/playground/index.ts:104–138](../examples/playground/index.ts): add a persistent associated URL label; announce loading/completion and errors in appropriate small live regions. Avoid making the full metadata/JSON output one noisy live region. React's plain loading/error divs also lack announcement semantics. Sources: [W3C labels](https://www.w3.org/WAI/tutorials/forms/labels/), [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).
- `website/assets/styles.css:226–235,278–280`: horizontally scrolling code/table regions have no explicit keyboard focusability/region names. Verify access at 320–375 CSS pixels and 200% zoom, particularly in browsers without automatic scroll-container focus; add focusable, named, visibly focused overflow regions where needed. This is a platform-supported verification gap, not a browser-reproduced failure. [W3C keyboard criterion](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html).

The documentation's current restrained design is appropriate. It already has semantic landmarks, skip navigation, current-page navigation, link/summary focus indicators, reduced-motion handling, and mobile native details navigation. No decorative redesign, imagery, font replacement, or animation is recommended by this audit.

### C4. Correct the Supabase setup journey — P2

[examples/supabase-edge-function/README.md:7–18](../examples/supabase-edge-function/README.md) deploys normally but demonstrates curl without authentication. Current default JWT verification rejects that request before the handler. Show a valid caller JWT from an environment variable **only to the Supabase endpoint**, and explain that endpoint credentials must never be forwarded to preview targets. Keep anonymous/public deployment as a separate deliberate choice. [Supabase Edge Function authentication](https://supabase.com/docs/guides/functions/auth). No deployment or authenticated account test was performed.

### C5. Describe caching precisely and align success policies — P3

The Cloudflare example sets `Cache-Control` on generated JSON but performs no shared-cache lookup/write and provides no Worker response-cache configuration. Every request reaching the handler still invokes `preview()`. Headers can help browser/downstream caching; they do not substantiate the site's claim that the edge absorbs repeated work. Either narrow the wording or implement/document the actual platform mechanism and verify reduced outbound fetches. [Cloudflare cache behavior](https://developers.cloudflare.com/workers/reference/how-the-cache-works/).

Website snippets use `statusCode < 400` while the standalone Worker/README use `>=200 && <300`. Align the successful-preview caching policy; an unfollowed 3xx need not be a usable preview. No examples were found forwarding incoming cookies or Authorization headers to arbitrary targets.

### C6. Remove the unused handwritten entity decoder in a focused cleanup — P3

`src/resolve.ts:1–65` contains `decodeEntities`, its entity map, and numeric helper; only the eight decoder tests in `test/resolve.test.ts:4–68` call it. It is not a public export. Commit `dbda3cace31de471dc35790003279c131c56da78` removed its parser use to fix double decoding but left the helper/tests.

Delete that dead source and its tests in a separately implemented cleanup. Retain URL resolvers and `test/parse.test.ts:380–405`, which protect real htmlparser2 single-decoding behavior. Expected deletion is roughly 65 production-source lines plus eight tests, not a demonstrated shipped-bundle speedup: the unused helper is tree-shaken. Keep public-export/package assertions and meaningful streaming boundary tests; no broad test deletion campaign is warranted.

### C7. Close the specific portability and example assurance gaps — P2

- Keep Bun and Deno CI, but add a small deterministic `preview()` stream/abort case: their current smoke tests mainly prove parsing/loading. Deno currently imports local dist rather than testing the advertised `npm:linkpeek` consumption path.
- Neither Cloudflare nor Vercel Edge is exercised by current CI; treat compatibility as an explicit claim to verify, not proof obtained from Node's typecheck.
- Framework examples are outside the root TypeScript configurations. Root typecheck does not establish React/Next/Express/Supabase integration acceptance.
- Keep live tests opt-in. Some full-corpus live assertions accept any title or even synthesized siteName; those can pass on challenge/error pages. Add status/minimal expected metadata where useful, while keeping network smoke distinct from deterministic regression proof.
- The website generator is small and dependency-free, validates page/route metadata, escapes template fields, and emits sitemap/llms/404 output. A static fragment check found one h1 per page and all nine local content links resolving. That does not prove external links, rendered layout, or accessibility.

### C8. Bound the playground rate-limit map — P2 before public deployment

`examples/playground/index.ts:9–20` keeps a module-level `hits` Map and inserts every new client IP. Expired records are reset only when the same IP returns; no path deletes old IPs or caps the map. Consequently a long-lived isolate retains all distinct visitors, including requests missing a preview URL because limiting runs before URL validation. This is a source-confirmed unbounded retention path, not a measured production leak or a demonstrated rate-limit bypass.

Use a bounded eviction/expiry policy for the demo, or the platform rate-limit mechanism when deploying publicly. Keep the existing warning that per-isolate limits are best-effort. Verify expired-key reclamation and a maximum retained-key bound without adding a test-only production export.
